### FND.0010 [medium] [inconsistency]
- **Location:** README.md title (line 14) vs its front-matter provenance
  and recipes/readme.md v0.15 (title instruction)
- **Issue:** The README title reads "Forge of Thought 2.5" while the
  recipe fixes the title to the current version of the forge intent and
  the render's own front-matter cites `10-intent.md v2.6`. The render is
  internally inconsistent and does not conform to its recipe.
- **Why it matters:** The README is this project's outward handover
  artefact and the title version is the one version number a reader is
  meant to trust (the recipe forbids any other). The intent's own v2.6
  changelog names a "2.5-titled README" pointing at stale notes as the
  very failure the round fixed — the title half of it is still present.
  It also shows the POS.0570 unconditional-re-render guarantee failing
  silently once.
- **Suggested fix:** Re-render (`/render readme`) — never a hand edit.
  Optionally have `/render` or `/check-forge` verify the title against
  the cited intent version so this class of miss is caught mechanically.

### FND.0020 [medium] [inconsistency]
- **Location:** 10-intent.md Version History rows 1.14/1.16 vs 1.24/2.4;
  POS.0210 closing note
- **Issue:** The ID THR.0120 was used for two unrelated threads. It first
  named "README recipe yet to be created" (opened v1.14, closed v1.16,
  also referenced in v1.15), then was reopened at v1.24 for the final
  form of the assignment-apparatus boundary and closed again at v2.4
  (cited in POS.0210). Reusing an ID for a different matter contradicts
  POS.0220 ("IDs are global and stable, never renumbered") — a closed
  ID's number should never be reassigned to new content.
- **Why it matters:** Citations of THR.0120 are now ambiguous: the
  Version History contains two different "THR.0120 closed" events meaning
  different things, and any future reader tracing POS.0210's provenance
  can land on the wrong thread. The ID scheme's whole value is that a
  reference is unambiguous forever.
- **Suggested fix:** Both threads are closed, so no live record needs
  renumbering. Record the collision once — e.g. a clarifying note in the
  next intent version's changelog or in POS.0210's parenthetical stating
  that THR.0120 (2026-08-15–17, assignment boundary) is distinct from the
  earlier THR.0120 (readme recipe, closed 2026-08-15) — and let new
  threads continue from the next genuinely free number.

### FND.0030 [low] [inconsistency]
- **Location:** decisions.md, header comment
- **Issue:** The comment still reads "whether to back-fill them here is
  THR.0070", presenting as open a question that DEC.0040 — in the same
  file — resolved on 2026-08-02.
- **Why it matters:** The file contradicts itself within one screen; a
  reader who trusts the header will go looking for an open thread that
  closed a fortnight ago. The header comment is scaffolding, not an
  append-only record, so it can be corrected without touching any DEC.
- **Suggested fix:** Update the comment to state the settled rule
  (design-phase REJ items are not back-filled; see DEC.0040).

### FND.0040 [low] [gap]
- **Location:** decisions.md DEC.0020 vs 10-intent.md POS.0450 and
  Version History v1.20
- **Issue:** DEC.0020 was materially generalised on 2026-08-15 (from
  "before the first draft" to "before the next layer is first derived",
  when the challenger was opened to any chain artefact), but the
  append-only decisions file carries no record of that change. Read
  alone, decisions.md states an outdated rule and references the retired
  `/draft` command; the only trace of the generalisation lives in the
  intent's changelog and a POS.0450 parenthetical.
- **Why it matters:** decisions.md presents itself as the record of
  decisions. A decision that has been superseded in substance with no
  superseding record weakens exactly the guarantee an append-only log
  exists to give. (The old record itself is correctly untouched —
  immutability is not the issue; the missing amendment is.)
- **Suggested fix:** Append a short DEC (e.g. DEC.0050) recording the
  2026-08-15 generalisation of DEC.0020, cross-referencing POS.0450 —
  or record a deliberate convention that DEC amendments live in the
  intent only, so the gap becomes a documented choice.

- The v2.6 Version History row folds two distinct working rounds (the
  release-notes decision and the same day's recipe-only README rounds)

  admittedly bump no intent version, but if they are worth recording in
  the intent at all, consider one row per round or a stated convention
  that recipe-only work is summarised into the next substantive row.
- POS.0180 has grown into a single ~40-line item covering ingest scope,
  bundles, indexes, dates, purposes, provenance and extraction tooling.
  As an intent position (audience: principal + Claude) this is
  legitimate, but if any part is ever handed over, consider splitting it
  into its natural sub-positions so future changes touch one idea each.
- The README title rule binds the render to a value (the intent version)
  that changes with every intent round; the mechanism that keeps it
  current is procedural (`/save` re-render). A mechanical cross-check in
  `/check-forge` (title vs cited input version) would make FND.0010's
  failure mode self-detecting.
