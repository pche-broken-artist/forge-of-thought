# Deterministic work: by script or by model

## Question

Does the forge meet this condition: everything that can be done
deterministically is done by a script, and nothing is given to the
model that does not need a model?

One question, answered from the engine's own files against the forge
intent. Quality comes first in the judgement: a step counts as
"needs a model" wherever a script would do it worse, not only where
a script could not do it at all.

## How it was read, and the marks

No web source was fetched for this note. The outside principle
(scripts for deterministic operations, hooks for what must hold every
time, checks by code before a model judge) was researched on
2026-10-03 and is cited from those notes, not repeated. Nothing was
run: no script, no check, no measurement of my own.

- **[F]** read in the forge's own file, at the place named.
- **[M]** a measurement recorded earlier in the project, cited.
- **[R]** a finding of an earlier research note, cited.
- **[S]** this note's synthesis or estimate, Claude's own.

## Answer in one paragraph

No. The condition is met at the edge of the forge and not at its
core. At the edge everything deterministic is a script: git, the
conversion of documents, the plain Word and PowerPoint files, the
per-prompt hook, the harness rules that keep the model from starting
a writing command. At the core the model does by hand, from prose,
the work a program does better: the bookkeeping of every write
(version, history record, `last_change`, ledger row), the numbering
and filing of findings, the provenance and staleness of renders, the
state map, the scaffold of a project, the rosters, and above all the
conformance checks, which the intent itself calls mechanical and the
engine runs as model agents at every save and every release. Two
things stand behind this and are more than debt: the condition is
not a position of the intent, and two positions decide the opposite
for the checks (POS.0540, POS.1140). [S]

## Key findings

### 1. The condition is not in the intent

- No position states it. A search of `10-intent.md` for the principle
  found only local uses: the plain file "deterministic, cheap,
  repeated freely" (POS.0590), the pandoc engine "needs no model"
  (POS.1150), and for handed-over work "what a test can tell ... is
  told by a test and not by his reading" (POS.1410). [F]
- Two positions decide the opposite for one family. POS.0540:
  "Mechanical conformance runs on the same mechanism as the critic
  and the challenger". POS.1140 gives the shape: one agent per check,
  on the session model. The reason given is "one mechanism for every
  reviewer"; cost and reproducibility are not weighed there. [F]
- Three positions use a mechanical word for a step a model performs.
  POS.0310: "a machine-written `last_change:` line, derived ... by
  the same write step ... never by hand", and "derivations by
  mechanism"; the write step is the model following prose. POS.0710:
  "`/render <recipe>` regenerates the output mechanically"; a render
  is generated by a model, as POS.0810 itself says ("Regeneration is
  stochastic"). POS.0930 calls the render "a mechanical job". [F]
- The matter is open in one place only: THR.0500 keeps "whether the
  filing is rewritten into a script", for the reviewers' filing and
  nothing wider. THR.0400 keeps the gate in front of the tools. [F]
- The outside guidance is unambiguous and already in the project:
  "Prefer scripts for deterministic operations"; "hooks are
  deterministic and guarantee the action happens"; the plan,
  validate, execute pattern; checks by code first and a model judge
  only where code cannot decide. [R] The note of 2026-10-03 on
  Anthropic's guidance ranks "bookkeeping by the model" fourth among
  the forge's departures and calls its move into scripts "the larger
  gain and the safer one"; the note on the operating layer names it
  option D. Neither classified the operations one by one; this note
  does.

### 2. Where the condition is met

| Operation | Done by | Where [F] |
|---|---|---|
| Commit, push, rebase, tag, the identity guard | script | `scripts/forge-save.ps1` |
| Pull, status, clone, branch | scripts | `scripts/forge-pull.ps1`, `forge-status.ps1`, `forge-clone.ps1`, `forge-branch.ps1` |
| Raw git kept from the model | harness rule | `.claude/settings.json`, `permissions.deny` |
| A writing command kept from the model's own start | harness field | `disable-model-invocation: true` in nine skills |
| No attribution trailer on a commit | harness setting | `.claude/settings.json`, `attribution` |
| The reminder at every prompt | script by hook | `scripts/hook-walkthrough.ps1` |
| Binary document to Markdown | script over markitdown | `scripts/doc2md.ps1` |
| Render to plain `.docx` or `.pptx`, A4 page | script over pandoc | `scripts/md2docx.ps1`, `md2pptx.ps1`, `-Engine pandoc` |

Here the forge is strict beyond the usual: reading git state goes
through a script too, and conversion "never by ad-hoc parsing". [F]

### 3. Where a model is rightly used

Elicitation of every artefact; the wording of positions; the critic
lenses and the challenger; the checks `single-source-of-truth` and
`history`, which compare meaning; a render's prose; the designed
file of `/publish`, a deliberate and stated choice (POS.0740,
POS.1150) kept apart from the deterministic plain file; research;
the What, Answer and Use lines of an index entry; the personal-matter
stop of `/ingest`; the one-line commit message; the summary of what
changed in a regenerated render; the translation `/man` makes into
the conversation language. None of these has a deterministic
equivalent of the same quality. [S]

### 4. Where the model does deterministic work

Ranked by what it costs, most first. "Mechanical" below means: the
right result is fully fixed by the files, and two runs must agree.

**4.1 The check `light`, run at every save.** Its Lens
(`.claude/agents/check-light.md`) lists: the placement of each
history and the form of its log; front-matter against the newest
records; the ledger's shape against the template; the Documents table
against front-matter and files; findings and challenges against the
files of `reviews/` and `challenges/`; every file of `sources/` and
`research/` registered; the Renders table against each render's
provenance; the Published table against `published/`; a retired
state word; every Dependencies path on disk, every outside citation
with a row; each index against its directory. Every one of these is
a comparison of files. Two clauses need reading: whether
"Waiting on principal" matches what is open where the line is free
text, and whether a `last_change` in prose agrees with its records.
[F] The Lens states its own cost as "seconds, not minutes"; measured
at the release of 4.49 it ran 131 to 160 seconds, four times
(THR.0410). [M] Both findings the check has filed so far were of the
mechanical kind: a subject outside the set the template allows
(FND.0730) and an ID named in `last_change` with no record at that
version (FND.0890). [F] Two findings are a small sample.

**4.2 The check `project`, run at every release.** Mechanical: the
`kind:` header, the repository's presence, the file set, recipes
paired with renders, provenance present, published files traced to a
recipe with a Format section, briefs against the Briefs table, a
mined brief cited in the intent, the whole of ID hygiene, the shape
of recipes against the skeleton, declared inputs on disk, the output
path inside the repository. Needs reading: the language of an
artefact, a Waiting line that copies where it should cite. One
clause the model cannot do and a script can: Immutables. The agent
has Read, Glob and Grep only and no git, so "never edited after
creation" is judged from signs; the report of 2026-10-03 says of a
related matter "I did not compare ... (no access to git)". A script
at the git door answers it exactly. [F] Measured: 315 seconds. [M]

**4.3 The check `engine`, run at every release of the engine.**
Mechanical: the Commands table against the skill directories, the
agents against their directory, every skill an agent names existing,
every script named in CLAUDE.md and the reverse, every DEC cited
from the intent existing. Needs reading: README against CLAUDE.md,
"every POS is honoured", every DEC reflected. Mixed: the rename
sweep is a search once the list of old names exists. [F] Measured:
405 seconds. [M]

**4.4 The filing of a report and the numbering of findings.**
`/check` step 1 has the session take "the next free `FND.NNNN`",
write the report "word for word" and add the ledger rows; the critic
and the challenger contracts have each agent take the next ID and
edit the ledger itself. Known and open as THR.0500; the ID race is
recorded in the note of 2026-10-02. [F] [R]

**4.5 The write of a round.** The version step, the date, the
agreement of status with the number, the records appended in the
shape of `templates/history.md`, `last_change` derived from them,
the ledger's Documents row. The judgement is in what changed and
why; everything after that is fixed by it. The step has no
definition of its own (debt 2 of the operating-layer note). [F] [R]
The intent's history holds 159 records written this way. [F]

**4.6 Provenance and staleness of renders.** `/render` step 5 has
the generating subagent write the front-matter with the versions of
the recipe and every input; step 6 has the session "verify ... its
provenance is correct" and mirror it into the ledger; step 8 sets a
Published row to `stale`. Staleness is defined as a comparison of
version strings and is then computed by the model wherever it is
shown (`/forge` map, `/publish` step 4). All of it is reading
front-matter and comparing. [F]

**4.7 The state map.** Bare `/forge` and `/ledger` report the kind,
the repository's presence, artefacts with version and status, which
states have their inputs, stale renders, dependencies cloned, what
waits. Only the last line, the recommended next step, is judgement.
[F]

**4.8 The scaffold of a project.** `/new-project` validates the
slug, refuses an existing directory, creates directories and copies
six to nine templates with slug, kind, language and date filled.
The model is needed for two questions and the brief. [F]

**4.9 The release notes.** The recipe has a model carry earlier
sections over "verbatim", map each record's kind to a group, and
copy each `Action` "word for word". POS.0730 says of the Action
that it "is never derived"; it is still transcribed by a model.
What needs a model is the sentence from the reader's side and the
choice of what reaches the reader. [F] Measured: 241 seconds. [M]

**4.10 The sweep of `/ingest`.** Files not in the ledger, files
modified after their registration date, the copy, the `-2` suffix,
the `.gitignore` line, the ledger row. The slug, the index entry
and the personal-matter stop need the model. [F]

**4.11 Rosters and the manual.** Five dispatchers and `/man` scan a
directory and print each file's `description`. [F] The platform can
inject a command's output before the model sees the skill. [R]

**4.12 `/setup`.** A file with constant content
(`settings.local.json`) and stanzas written into the user's global
git configuration are produced by the model; the second is an edit
outside the engine, the one place where an exact program is also the
safer hand. [F]

**4.13 Small ones.** `/release` reads the branch from the status
script's output and decides itself whether it is `main`; the script
could refuse. The tag `v<major>` at an integer version is a rule the
model applies. Prose is wrapped at 72 columns by the model. The
default engine of `md2pptx.ps1` is the model while that of
`md2docx.ps1` is pandoc, so a bare call of one converts by model and
of the other by program; `/render` names the engine and is
unaffected. Mermaid has no deterministic path into a document.
[F]

**4.14 Rules kept by the model's own discipline.** Not work but
enforcement: "use the script", "ask before a command of your own",
"write nothing not agreed" are five printed lines; the hard half is
THR.0400. The same principle one level up. [F] [R]

### 5. What the present way costs

- Time at a release of the engine: `light`, `project`, `engine` and
  the release notes add up to more than a quarter of an hour of
  isolated model runs, most of it on mechanical clauses. [M], the
  share is [S]
- Every reviewer run carries the whole CLAUDE.md (THR.0240). [R]
- No reproducibility: a model check that reports "conforms" has not
  proved it read every row; a second run may find what the first did
  not. A script reads every file every time. [S]
- No test: "the scripts are the one part that could be tested by
  ordinary means today" (operating-layer note), and none of the work
  above is in a script. [R]
- The ID race and the drift between a document and its bookkeeping,
  which is what the `light` check then exists to find: part of what
  it finds is produced by the write step being done by hand. [S]

### 6. Why it is this way, and what a script costs

The present way has one real merit: a model check reads each rule at
its owner at run time, so it never lags a convention, and the forge's
conventions change almost daily. A script fixes a shape in code.
THR.0500 already names the price: "the shape would stand in two
places". Three more: Markdown tables are a poor store for a program
(operating-layer note); a save would need the script's language on
every machine, which today only conversion does (THR.0150); and a
script's finding needs a stable identity, so that a finding rejected
by a DEC is not raised again, which the model does today by reading.
Whether the history log parses without guessing where a reason or a
`Was` contains the field separator was not tested. [S]

## Options with trade-offs

**A. Leave it and decide nothing.** No work, no risk of a shape in
two places. The condition stays unmet and the cost of 5 is paid at
every save and release.

**B. State the principle, convert as touched.** One position: what
the files fully determine is done by a program, the model is kept
for judgement, and a mechanism names which of its steps are which.
Each mechanism is brought to it when next worked. Cheap to decide;
slow to take effect; needs POS.0540 and POS.1140 reworded, since
they decide the checks otherwise.

**C. A conformance script first.** One program with the mechanical
clauses of `light`, then of `project` and `engine`, reading table
headers and the record shape from the templates where it can. The
save runs the program; the model agents keep only the clauses that
need reading and get the program's output as a fact. Largest gain
for the least change of behaviour: nothing the model is told
changes, it is only told less. The price is the script's upkeep
with every change of convention, and tests to carry it.

**D. The write path as plan, validate, execute.** The model writes
the round's changes as one structured file; a program validates it
and applies IDs, records, `last_change`, ledger rows, and files a
reviewer's report the same way. Removes the cause of most
bookkeeping findings and the ID race. The largest change, on the
most used mechanism; it touches how every write is reflected back
to the principal.

**E. The small deterministic pieces.** The scaffold, the state map,
render provenance and staleness, the release-notes assembly with the
model writing only the reader's sentences, rosters by injection.
Each is independent and small; none removes the main cost alone.

C, D and E are the work B would order; they do not exclude each
other.

## Relevance to this project, with a recommendation

Epistemic status: synthesis, Claude's own; the decisions are the
principal's.

1. **Decide the principle first, as a position (option B).** Today
   the engine cannot be said to break a rule, because the intent has
   none; it has the opposite decision for the checks. Proposed
   through `/forge intent`, never written here.
2. **Then option C, beginning with `light`.** It runs at every save,
   it is almost wholly mechanical, both findings it has filed were
   mechanical, and a first script written in Python is what POS.0830
   already asks of a new script. The agents `project` and `engine`
   shrink to their reading clauses afterwards.
3. **Then the filing and the numbering (THR.0500), then option D.**
   In that order, because the conformance script gives D its
   validator.
4. **Option E as each piece is next touched.**
5. **Keep with the model**, by the same principle: everything in
   finding 3, and the checks `single-source-of-truth` and `history`
   whole.
6. **Two wordings of the intent to mend with it**: "machine-written"
   in POS.0310 and "mechanically" in POS.0710 describe a model's
   step.

What would change this recommendation: a trial showing that the
script's upkeep under changing conventions costs more than the model
runs it replaces; that is measurable only once the first script
exists.

## What stays uncertain

- How long a conformance script would run: expected seconds, not
  measured. [S]
- The token cost of each check run: not measured anywhere in the
  project; only durations are recorded.
- How many of the conformance findings filed to date a script would
  have found: only the two `light` reports were read for this note;
  the reports of `project`, `engine` and `single-source-of-truth`
  were not classified.
- Whether the history log and the ledger tables parse without
  guessing: not tested.
- Whether a language detector is good enough for the Language clause
  of `project`: not looked at; left with the model here.
- The operating layer was being edited by another hand while this
  note was written (CLAUDE.md changed on disk during the reading);
  places are cited as read on 2026-10-04.
