# How project documentation is built

## Question

How should the documentation of an open project of the forge's kind
be built: what the recognised standards and frameworks say, how the
README and the documentation divide, how the documentation lives in
a git repository, and how its pages are structured and linked?

The facts behind the question. The README is today the whole
documentation: sixteen numbered chapters, 829 lines on 2026-09-08
(THR.0340), generated by a model from one recipe at every release,
and three things at once: an invitation, a user's guide and a
reference. The draft brief `next-gen` wants a short README (what the
forge is and what it is for) and the documentation as "a normal
series of documents on single topics, separate linked pages", for
readers inside a company and outside it. THR.0340 has already
decided the split in substance (2026-09-08): a short README, the
guide and the reference as renders of their own recipes into
`docs/`, ordered after the engine/framework boundary of THR.0230.
The news of a version and the release notes are a sibling research
and are left out here.

**How to read the marks.** Practice: **[C]** consensus, **[E]**
emerging, **[X]** contested. Evidence: **(V)** read at the source on
2026-10-03, **(S)** taken from a secondary source or a search result,
**(O)** this note's own synthesis. One caution covers every (V): the
fetch tool used does not return the page itself but a summary of it
made by a small model, with quotations it reports as verbatim. The
quotations below are those reported quotations; none was checked
against the raw page. Lengths of other projects' READMEs are that
model's estimates, not counts.

## Key findings

### 1. Diátaxis is the reference frame for structure; it is a way of sorting, not a table of contents [C]

Diátaxis sorts documentation by the reader's need into four kinds
(V, diataxis.fr/start-here): a **tutorial** is "a lesson, that takes
a student by the hand through a learning experience"; a **how-to
guide** "addresses a real-world goal or problem" for "an
already-competent user"; **reference** holds "the technical
description - facts - that a user needs in order to do things
correctly", "free of distraction and interpretation"; **explanation**
gives "context and background" and serves "the need to understand".

What it says about each kind matters for the forge's pages (V, the
four pages of diataxis.fr):

- Reference: "the structure of the documentation should mirror the
  structure of the product"; "Reference material is useful when it
  is consistent"; it may be generated, with the warning that "too
  many software developers think that auto-generated reference
  material is all the documentation required".
- Explanation: covers "the bigger picture, history, choices,
  alternatives, possibilities, why: reasons and justifications"; it
  is the neglected kind because it "tends to be scattered in small
  parcels in other sections"; titles of the form "About ...".
- How-to: "practical usability is more helpful than completeness";
  titles "that say exactly what a how-to guide shows".
- Tutorial: "not the place for explanation" (link to it instead);
  must work "for every user, every time"; the most expensive kind to
  keep, because in a tutorial changes "often cascade through the
  entire story".

Its guidance on adoption is explicit and gradual (V,
diataxis.fr/how-to-use-diataxis): "Diátaxis changes the structure of
your documentation from the inside"; it does not mean "that you
should create empty structures for tutorials/howto
guides/reference/explanation with nothing in them. Don't do that";
"Diátaxis is designed to guide small steps"; choose one small thing,
improve it, publish it. The four kinds are a test applied to a page,
not four top-level folders to fill.

Adoption (V for each): the BMAD Method's style guide says it "uses
Diataxis to structure content"; Spec Kit's site has Getting Started,
Reference and Concepts; the Python documentation community adopted
it as a guide in April 2022.

### 2. The criticism of Diátaxis is about what it leaves out, not about the four kinds [X]

- It gives general guidance, not a plan: in the Python discussion
  (V, discuss.python.org, 2022-04) the objection recorded was that
  the framework "can only provide general guidance, whereas a North
  Star ... would provide specific long term goals", and that a page
  mixing reference and how-to has no obvious fate.
- It looks arbitrary as an information model: a technical-writing
  commentator (V, idratherbewriting.com, 2023-10-18) first found
  that "Siloing documentation into tutorials, how-tos, reference,
  and explanation seemed overly opinionated and arbitrary", and
  reports the framework author's answer that it "isn't meant to
  impose four rigid buckets". The same piece notes that Diátaxis has
  no mechanism for new types and no concern for reuse, both of which
  DITA has.
- Getting-started, landing, troubleshooting and glossary pages have
  no home of their own (S, search summaries of several pieces; DITA
  1.3 does define troubleshooting and glossary types, V). Diátaxis'
  own page on complex hierarchies, which treats landing pages and
  the case of two structures crossing (kinds against topic areas or
  user types), could not be fetched; its content is known here only
  from search summaries (S).

Practice answers the gap the same way everywhere read (V, the five
projects of finding 8): the top level of the navigation is the
reader's journey or the product's areas (Start, Build, Customize,
Reference), and the four kinds discipline the single page. Pure
four-folder navigation was found in none of them. **[C]** for the
page-level use, **[X]** for the kinds as top-level navigation.

### 3. The older lineage says the same at the page level [C]

- Topic-based authoring, DITA 1.3 (V, OASIS specification, 2015):
  typed topics, the base three being **concept**, **task** and
  **reference**, later joined by troubleshooting and glossary. One
  topic, one type. Diátaxis' how-to, reference and explanation map
  onto task, reference and concept (O); the tutorial is the addition.
- Every Page is Page One (V, the book's own page; published 2013):
  "People don't arrive at your site, they arrive at your pages."
  A topic is self-contained, has "a specific and limited purpose",
  conforms to a type, establishes its context because a reader "can
  arrive ... from anywhere", stays on one level, and links richly.
- The Good Docs Project (V, its template list): templates per page
  type, each a pack of template and guide; the core pack is concept,
  how-to, README, reference, release notes, troubleshooting and
  tutorial, with quickstart, installation guide and glossary among
  the rest. Its README guide (V, the guide in its repository) wants
  the README "succinct" so that "users do not need to read pages to
  understand why they should be interested", linking out to getting
  started and quickstart documents.
- Google's developer documentation style guide (V, last updated
  2026-04-27 as reported) is a style guide, not a structure
  framework; its use here is the linking rules: "Be selective about
  which links you include on a page. Each link creates a decision
  for the reader"; link text that "makes sense without the
  surrounding text", never "click here"; no duplicate links to one
  destination on a page.
- Write the Docs' principles (V): **Current**, "Consider incorrect
  documentation to be worse than missing documentation"; **Unique**,
  "Eliminate content overlap between separate sources"; **Nearby**,
  "Store sources as close as possible to the code which they
  document"; **Addressable**; **Cumulative**, prerequisites first;
  and against them **ARID**, "Accept (some) Repetition In
  Documentation". Google's documentation best practices (V) add
  "A small set of fresh and accurate docs is better than a large
  assembly of 'documentation' in various states of disrepair" and
  "Delete dead documentation".
- Docs-as-code (V, Write the Docs): documentation written "with the
  same tools as code": version control, plain-text markup, review,
  automated tests. The forge already is this; nothing to adopt.

### 4. The README orients and points; it is not the manual [C]

Every source read gives the README the same job and none gives it
the documentation's:

- The hosting platform (V, GitHub's page on READMEs): a README says
  what the project does, why it is useful, how to get started, where
  to get help, who maintains it. And of the rest: "Longer
  documentation is best suited for wikis" (the venue is contested,
  finding 6; the division is not).
- Google's README guidance (V): what the package is and is for, how
  to use it, status, contacts, and links to the documentation; a
  good README "orients the new user ... and points to more detailed
  explanation and user guides".
- Make a README (V): name, description, visuals, installation,
  usage, support, roadmap, contributing, licence, status; "too long
  is better than too short", but when it grows, "consider utilizing
  another form of documentation rather than cutting out
  information".
- Standard Readme (V, its specification): a fixed order of title,
  short description "less than 120 characters", table of contents
  (optional under 100 lines), install, usage, contributing, licence
  last; a long description goes to a Background section.
- The Art of README (S, not reachable at source; known from search
  summaries): "cognitive funnelling", the most general first (name,
  description, example), narrowing to specifics, so that a reader
  can leave early with the right answer.
- Curated practice (V, the awesome-readme list): the READMEs praised
  are praised for a clear description, a demonstration, install and
  usage that are easy, and clear pointers to where more is found.

Length (V for the pages, the numbers being the fetch model's
estimates): of the five comparable projects, the READMEs run from
about 250 words (one screen and a link) to about 2,800 words; the
two with the largest documentation sites have READMEs of roughly
1,200 to 1,500 words. The forge's README is several times the
longest of them. No source read prescribes a number; what they
prescribe is the content, and the content excludes the guide and
the reference. (O)

Beside the README the platform recognises a small set of community
health files (V, GitHub): CONTRIBUTING, SUPPORT, SECURITY,
CODE_OF_CONDUCT, each in the root, `.github` or `docs`. They are
the standard homes for what would otherwise swell a README.

### 5. Where documentation lives: three models, and a small project is advised to stay with files [C on the trade-offs, X on the choice]

**Plain Markdown in `docs/`, read on the hosting platform.** The
platform renders every Markdown file, builds an outline of its
headings, and resolves relative links on the current branch (V,
GitHub): "The path of the link will be relative to the current
file"; relative links are recommended because "absolute links may
not work in clones". Heading anchors are generated from the heading
text, and "if you edit a heading ... you will also need to update
any links"; a custom anchor is an HTML `<a name>`. Nothing to build,
nothing to host, the documentation of a tag is the files at that
tag. What it lacks: a sidebar, search across pages other than the
platform's code search, and a designed landing page. Navigation is
by an index page and by links in the pages. OpenSpec does exactly
this with about 26 pages (finding 8).

**A static site generated from the same files.** What each needs
and gives (V for each tool's own page unless marked):

- MkDocs: Markdown in `docs/`, one `mkdocs.yml`, navigation either
  declared or discovered from the files, links between pages as
  relative `.md` paths with anchors, which is the same link form the
  hosting platform resolves. But the makers of its dominant theme
  state (V, 2025-11-05) that "MkDocs must be considered a supply
  chain risk, since it's unmaintained since August 2024" and that
  "Material for MkDocs is in maintenance mode", with fixes promised
  for at least twelve months and a successor generator announced.
- Docusaurus: a Node and React site; versioning by copying the whole
  docs folder per version, with its own warning: "Most of the time,
  you don't need versioning as it will just increase your build
  time, and introduce complexity to your codebase."
- Starlight: a documentation theme on the Astro framework, Markdown
  under `src/content/docs/`, sidebar, built-in search,
  internationalisation; no built-in versioning reported.
- mdBook: a book defined by one strict `SUMMARY.md`; "Without this
  file, there is no book".
- VitePress: a Vue-based generator; no built-in versioning reported.
- Hosting: GitHub Pages publishes from a branch and its root or
  `/docs` folder (Jekyll as the built-in build) or from a workflow;
  Read the Docs builds every branch and tag as a version, with
  `latest` and `stable`.

A site buys navigation, search, a landing page and a public address
that search engines index. It costs a toolchain, a configuration, a
build and a deployment to keep alive, and a second place where the
documentation can be broken. The MkDocs case shows that the
toolchain itself can lapse under the project. (O)

**A wiki.** GitHub recommends it for "long-form content" (V), but
its own page states the limits: "Search engines will only index
wikis with 500 or more stars that you configure to prevent public
editing". A wiki is a separate store outside the repository's tree,
so it does not travel with a tag or a clone and is outside review
(S for the separate store; from general knowledge, not fetched).
None of the five comparable projects uses one (V).

**What a small project is advised.** The one piece found that
answers directly (S, a search summary of a 2026 guide for package
authors): a documentation site "is infrastructure that must be
built, hosted, and kept in sync", many projects are better served
by organised Markdown, and a site earns its place when the
documentation needs search, several integration paths or versions
side by side. This agrees with Diátaxis' small steps and Google's
minimum viable documentation; it is advice, not a standard. **[X]**:
the large comparable projects all moved to a site once they had an
audience.

**Versioned documentation.** Where the documentation is files in
the repository, the version is the tag (O). Side-by-side versions
on a site are advised only for projects with many users on old
versions (V, Docusaurus).

### 6. Two readers: the agent reads the definitions, the human reads the pages; conventions for agents are emerging and thinly evidenced [E]

- **llms.txt** (V, llmstxt.org): a proposal of 2024-09-03, still "open
  for community input": a Markdown file with an H1, a blockquote
  summary and lists of links with descriptions, plus the convention
  that every page is also available as plain Markdown. Adoption grew
  about ninefold in a year, yet a log study of 137,000 domains found
  that "97% of llms.txt files received zero requests" in May 2026
  (V, a trade report of 2026-07-02 citing both studies; the studies
  themselves not read). The same report separates crawlers, which
  ignore the file, from agents fetching documentation on a user's
  behalf, which are its intended reader.
- **Claude Code's documentation** uses it in exactly that second
  sense (V): `llms.txt` indexes some 220 pages as `.md` files with a
  one-line description each, and every page opens with a pointer for
  an agent: "Fetch the complete documentation index ... Use this
  file to discover all available pages before exploring further."
- **AGENTS.md** (V, agents.md): "README.md files are for humans";
  the agent's file carries "the extra, sometimes detailed context
  coding agents need", kept apart so as to "keep READMEs concise".
  Three of the five comparable projects carry one (V).
- **What is known about generated text for agents.** A controlled
  study (V, the abstract of arXiv 2602.11988, submitted 2026-02-12)
  found that "providing context files does not generally improve
  task success rates, while increasing inference cost by over 20% on
  average"; secondary reports of the paper (S) add that
  model-generated files lowered success slightly and hand-written
  ones raised it slightly, and that broad overviews were the
  ineffective part. This is about context files for coding tasks,
  not about user documentation; it is the only measured evidence
  found on generated prose in this neighbourhood.
- **Generated documentation going stale or verbose.** Only vendor
  surveys and opinion pieces were found (S): that generation without
  maintenance produces more documents to go stale, and that a model
  writes fluent text which misses the reasons behind a design. No
  primary study of generated user documentation was found. Weak
  evidence, recorded as such.
- **Single-sourcing.** The frameworks agree on the division (V,
  Diátaxis reference page; O for the rest): reference can be derived
  from the thing it describes, because its job is to mirror it;
  tutorials, how-to guides and explanation cannot, because their
  content is a judgement about the reader. Write the Docs' "Unique"
  and Google's "Duplication is evil" argue for deriving or linking
  rather than restating.

### 7. The page level [C]

Drawn from findings 1 to 3 and the projects of finding 8:

- One topic and one type per page; the type decides the shape. The
  BMAD Method's style guide (V) fixes a template per type (tutorial,
  how-to, explanation in four variants, reference in five) and a
  budget of headings per page; the Good Docs Project ships a
  template and a guide per type.
- A page establishes its own context, since the reader may land on
  it first (V, Every Page is Page One).
- Two paths through the same pages: a start path for the new reader
  (overview, install, first result) and reference for the returning
  one. Claude Code's overview (V) installs in a few lines, hands on
  to the quickstart, and ends in a "Next steps" list; OpenSpec's
  index (V) is grouped "Start Here", "Use It Day to Day",
  "Understand It Deeply", "Make It Yours", "When You Need Help" and
  routes by the reader's situation.
- Concept pages that say why are a kind of their own and the one
  most often missing (V, Diátaxis). Spec Kit has a Concepts group,
  Agent OS a Concepts group, OpenSpec a concepts page (V).
- Links are few and descriptive (V, Google). Where a generator
  supplies a sidebar, pages carry no "Related" or "Next" sections
  (V, the BMAD style guide: "Sidebar handles navigation"); without a
  generator the page itself must carry the way back to the index and
  onward (O).
- No source read gives a length for a page. What is given is the
  test: one purpose, and what is not of that purpose is linked.

precedent exists (OpenSpec), and it is a successful one.

## Options and trade-offs

Two independent choices: where the pages live and how they are
made. A third, what the first set is, follows.

### Where the pages live

**A. Plain Markdown pages in `docs/`, linked from a short README;
`docs/README.md` as the index.** Nothing to build or host; the
documentation of a version is the tag; relative links work on the
platform and in a clone; the pages are already the plain Markdown
an agent wants. *Against:* no sidebar and no search of its own;
navigation rests on the index and on links kept right by hand or by
a check; heading anchors break when a heading is reworded; less
inviting to an outside reader than a site.

**B. A generated static site over `docs/`.** Sidebar, search, a
landing page, a public address. *Against:* a toolchain, a build and
a deployment for one maintainer; a new dependency class (Node or
Python) for an engine whose scripts are its only platform-bound
layer; the generator may lapse (finding 5); a public site presumes a
decision on the public boundary (THR.0210) that has not been made.
It can be added over A later without rewriting pages, provided A's
links are relative `.md` links (V for MkDocs' link form; O for the
conclusion).

**C. A wiki.** *Against:* outside the repository's tree, the tag,
the clone and the release mechanism; not indexed for a small
project. No comparable project uses one.

### How the pages are made

**1. Rendered from recipes, as the README is.** The mechanism
exists (a recipe's `output:` path, the Renders table, `/release`).
Two cuts: *one recipe per page* (each small, with its own inputs,
re-rendered only when its inputs changed) or *one recipe per page
type* producing many pages (fewer recipes, but one long generation
whose failure or drift touches every page). The forge's own terms
suggest a third reading: the page type is a **genre** (a skeleton
per type, as finding 7's templates are), the page a **recipe**.
*For:* single source in the intent and the definitions; nothing is
written twice. *Against:* cost and time per release grow with the
page count (the README alone took five to eight minutes); a model
re-wording stable pages at every release produces diffs with no
change of substance; the weak but consistent signal that generated
prose is verbose and that broad generated overviews help least
(finding 6).

**2. Reference derived mechanically, the rest rendered or written.**
The reference the forge needs (the commands, the rosters of lenses,
personas and checks, the scripts, the ID prefixes, the document
kinds, the layout) already has owners with machine-readable heads:
front-matter `description`, help headers, tables. `/man` reads them
for the agent at the moment of the call. The same reading, done by
a script, gives reference pages that are deterministic, cheap and
never re-worded. *For:* matches Diátaxis' division; removes the
largest and most volatile third of today's README from the model's
hands. *Against:* a new script to write and keep; a mechanical page
is terse and needs one hand-kept sentence of context at its head.

**3. Pages composed by hand (by the principal with Claude), as
chain artefacts are.** *For:* explanation is judgement and reads
best when composed. *Against:* a second place for what the intent
already holds as positions with reasons; by the forge's own boundary
a composed page is not a render, so it would be a new document kind,
which is a convention to decide and not a by-product.

**4. The conventions reference not rendered at all:** the
documentation links to `CLAUDE.md` and the definitions, which are
readable as they stand (the open point of THR.0340). *For:* "Unique"
and "Duplication is evil"; zero cost. *Against:* those files address
the agent, not a human newcomer; a link out of `docs/` into the
operating layer is a harder read than a table.

## Relevance to this project

The sources agree with what THR.0340 already decided and with the
brief: the README invites and points, the documentation is separate
pages of one topic and one type each, and reference is one group
among several ordered by the reader's journey. Nothing found argues
for keeping the single file. What the research adds is how.

**Recommendation** (this note's own synthesis, for the principal to
decide through `/forge intent`; each point is a proposal):

1. **Where: option A now, B left open.** Plain Markdown pages in
   `docs/` with `docs/README.md` as the index, relative `.md` links
   throughout, so that a site can later be laid over the same files.
   A site is a decision that belongs with the public boundary and
   the rollout, not with the split.
2. **How: option 2 with 1 beside it.** Reference pages derived
   mechanically from the definitions that own them (the reading
   `/man` already does); the start path, the how-to pages and the
   concept pages rendered from recipes, one recipe per page, the
   page type as a genre. Composing pages by hand (3) is not needed
   while the intent carries the reasons. On the open point of
   THR.0340: a derived conventions page is cheap enough to have, so
   the question of linking to `CLAUDE.md` instead largely falls
   away.
3. **Re-render only what changed.** With one recipe per page, a
   release need regenerate only the pages whose inputs moved; the
   ledger already knows `current` and `stale` for published files.
   This answers the cost objection of THR.0340 and the re-wording
   objection together. How staleness is told is a design question,
   not answered here.
4. **The README.** What the forge is, for whom, what one gets, the
   quickstart, where the documentation is, licence. The masthead and
   sections 1 to 3 of today's README are close to this already; the
   remaining thirteen chapters are the pages.
5. **A first set of pages by type**, as a list to sift, not a
   design:
   - *Start path:* installation and first run; a first project from
     brief to intent (a tutorial, the most expensive page, which
     honestly waits for the worked example of THR.0200; until then a
     quickstart).
   - *How-to:* bring in a source; run a reviewer and settle its
     findings; make a render and a published file; save and release;
     upgrade the engine and migrate a project; bring in an existing
     project.
   - *Concepts ("About ..."):* the document chain and why the intent
     exists; the working methods; isolated reviewers and why
     isolation is not independence; renders and recipes; versions
     and history.
   - *Reference (derived):* commands; reviewers' rosters;
     conventions (IDs, document kinds, versioning); repository
     layout; scripts; a glossary.
   - *Later, when there is material:* troubleshooting or FAQ.
6. **Start small, no empty structure.** Diátaxis' own advice fits
   the forge's iteration: cut the README first, move chapters out as
   pages one at a time, improve each as it moves.
7. **On the decided order (after THR.0230).** The reason given was
   that a `docs/` cut made now would be cut again along the
   engine/framework line. With pages of one topic each, that line
   moves whole pages between repositories and re-cuts few of them;
   the reason to wait is weaker for pages than it was for two long
   documents. This is new ground for the principal to weigh, not a
   reversal proposed here.
8. **For the agent, nothing new.** `/man` over the definitions is
   already single-sourced documentation read on demand, which is
   what the emerging conventions aim at. An index page with one line
   per page is the `llms.txt` form in all but name; a file of that
   name is worth adding only if a public site comes.
9. **A check on links.** Plain Markdown has no build to catch a
   broken relative link or anchor; a mechanical check of the links
   in `docs/` is the natural counterpart (a new check is the
   principal's decision).

Trade-off stated once: A with 2 gives the least to maintain and the
most stable text, at the price of no sidebar and no search for the
outside reader. If the rollout makes the outside reader the first
audience, B moves forward, and the choice of generator should then
be researched afresh, since that ground shifted within the last
year.

**What stays uncertain.** Two sources named in the question were not
read at source (Diátaxis' page on complex hierarchies, the Art of
README). README lengths are estimates. Whether generated user
documentation measurably goes stale or verbose has no primary
evidence either way. How relative links and outlines behave on
hosting platforms other than GitHub was not read. The page budget
that one release can afford to render was not measured.
