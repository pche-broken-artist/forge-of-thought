# What the forge is made of

The operating layer of the forge is a set of files that Claude Code
reads, with the deterministic work kept in scripts at its edge. The
forge is not a program. This page is for the extender: someone who is
about to change or add one of those files. It says which files there
are, what each one is and when each one is loaded, so that you can find
the right file before you touch it.

## When to use it

Use this page before you change the forge. It helps you find the file
that holds what you want to change. It also tells you when that file is
in force: always, or only when its situation arises. How a change is
made and recorded is described in
[Make a change to the forge](how-a-change-is-made.md).

## What you do

Find the file in the table. The paths are relative to the engine root.
The full layout block is on
[Repository layout](../reference/repository-layout.md), and every
skeleton is on [Templates](../reference/templates.md). A term you do
not know is on the [Glossary](../reference/glossary.md).

Two words appear in the table:

- session: one run of Claude Code, from its start to its end.
- subagent: a separate Claude that a command launches. It sees only
  the files it is given and never the working conversation.

The line of flow: you type a command, its skill loads on top of
`CLAUDE.md`, the skill reads a definition or a template, launches
agents with their contracts as subagents and runs scripts, the result
lands as files in the project, and a script commits it to git.

## What happens

Five ideas carry the layer. Each one tells you where a kind of change
belongs.

- One always-on core, the rest read on demand. `CLAUDE.md` is loaded
  everywhere. A command, a definition, a contract or a template is
  read only when it is invoked. What must hold through a long
  conversation is repeated by the hook at every prompt.
- State lives in Markdown files of the project. It never lives in the
  conversation or in the assistant's memory. A project is a directory:
  the artefacts of the chain, their history logs, the ledger, the
  records of the reviewers and the resources.
- Isolation comes from subagents. A reviewer, a check and a render
  each run in a subagent, all on the one session model.
- Git, the conversion of documents and the hook are scripts. The
  harness (that is, Claude Code, the program that runs Claude and
  enforces the settings) denies Claude raw `git`. The scripts are
  therefore the only door to git.
- Every file has a way of merging, and the forge tells git which one.
  Records merge as sets by a driver. Derived state is made at read
  time and never kept in git. Composed text merges as text. The forge
  still merges nothing itself.

Why the core is small and the rest is loaded on demand is explained in
[How the rules are held](../about/how-the-rules-are-held.md).

You should now see which file holds the rule you want to change, and
whether that rule is in force always or only when its situation arises.

## A worked example

One command traced through the layer: a critique of the intent of a
project with the placeholder slug `my-project`.

```
/critique clarity intent my-project
```

1. `CLAUDE.md` is already loaded, because it is loaded in every
   session. The principal (the person whose thinking is being forged)
   types the command.
2. Claude Code loads `.claude/skills/critique/SKILL.md`, the skill of
   the command.
3. The skill launches the agent `.claude/agents/critic-clarity.md` as
   a subagent. The agent file names `critic-contract` in its
   front-matter, so `.claude/skills/critic-contract/SKILL.md` is
   preloaded into it at launch. The agent reads the intent of
   `my-project` and never the working conversation.
4. The agent returns its report with its findings unnumbered and
   writes nothing.
5. The command gives the findings their IDs and files the report in
   `projects/my-project/reviews/`. The name of the report is completed
   by `scripts/forge-report.py`.
6. The findings are settled by walkthrough. A walkthrough is the
   working method that takes one item per message, each closed with a
   verdict. `.claude/skills/walkthrough/SKILL.md` is read for it. The
   verdicts are written in one round.
7. `/save` commits and pushes through `scripts/forge-save.py`, the
   only door to git.
