# What the forge is made of

The operating layer of the forge is the set of files that Claude Code
reads and runs: one always-on core, the skills, the agents, the
settings, the templates and the scripts. This page is for the
extender, the person who changes or adds to the forge. It tells you
which file holds what, and when each one is loaded, so that you know
where a change belongs before you make it.

## When to use it

Use this page before you change any part of the forge.
It answers three questions: which file owns the thing you want to
change, what kind of file that is, and when Claude reads it.
How a change is then made, recorded and released is described in
[Make a change to the forge](how-a-change-is-made.md).

## What you do

Find the thing you want to change in the table below.
Open the file at its path.
Every path is relative to the root of the engine (the one
installation of the forge that holds the projects).

| Path | What it is | Loaded when |
|---|---|---|
| `CLAUDE.md` | The universal core: the roles, the prime directives, the working methods in short, the document kinds, the chain, the layout, persistence, versioning, the ID scheme, the reviewers, the ledger and the list of commands. | In every session and in every subagent, always. |
| `.claude/skills/<name>/SKILL.md` | One skill per command. | When the command is invoked; until then its body is not read. |
| `.claude/skills/forge/states/<state>.md` | The definitions of the artefacts: supporting files of the `/forge` command, one per target state. | When `/forge` reads the definition of the artefact it works, by path. |
| `.claude/skills/recipe/genres/<genre>.md` | The genre files: supporting files of the `/recipe` command, one per genre. | When `/recipe` reads the genre it is asked for, by path. |
| `.claude/skills/<kind>-contract/SKILL.md` | The three reviewer contracts (critic, challenger, check): skills that are not commands and stay out of the `/` menu. | Preloaded into each reviewer agent that names it in its front-matter, when that agent starts. |
| `.claude/skills/docs-contract/SKILL.md` | The documentation contract: what the documentation's planner and writer share. Not a command. | When the documentation's planner or writer runs. |
| `.claude/skills/walkthrough/SKILL.md` | The shape of the walkthrough and of the elicitation interview. Not a command. | Whenever a walkthrough or an interview runs. |
| `.claude/agents/` | One file per critic lens, per challenger persona and per check, and the documentation's planner and writer. | When a command launches that agent as a subagent. |
| `.claude/settings.json` | The two hooks and the deny rule of the other shell. | Read by the harness; the per-prompt hook runs at every prompt, the git hook before a tool is used. |
| `templates/` | The canonical skeletons of every new document, the skeleton of the player page among them (`templates/html-player.html`). | When a command makes a document from its skeleton. |
| `scripts/` | The Python scripts, with the modules they share beside them (`forge_repos.py`, `forge_tools.py`, `forge_docs.py`, `docs_map.py`). The two hooks are scripts too. | When a command, a hook or you run one as `python scripts/<name>.py`. |
| `.gitattributes` | The engine's own ways of merging by path, for its derived files at the root and under `projects/forge/`. | By git, when it merges. |
| `tmp/` | The engine's working folder: what scripts and commands make on the way to a result. | Read by no check, no ledger and no history. |
| `projects/forge/` | The forge's own project: Forge of Thought run through its own process. | Like any project, when a command works on it. |
| `docs/` | The generated documentation: pages of one topic each and their index. | Never read as a source; regenerated by `/document`. |
| `docs/videos/` | The public folder of the projects' videos and the player page; not part of the documentation. | Served as public pages; left alone by `/document`. |

Some words in the table need a gloss:

- A session is one conversation with Claude Code.
- A subagent is a separate Claude run that sees only the files it is
  given, never the working conversation.
- The harness is Claude Code itself, the program that loads the files
  and runs the hooks.
- A hook is a script the harness runs at a fixed moment.
- The principal is the person whose thinking is forged.
- The ledger is the single source of truth for the state of a
  project, made from the documents at read time.

Every other term is in one line in the [Glossary](../reference/glossary.md).
The full block of directories is on the page
[Repository layout](../reference/repository-layout.md), and every
skeleton on the page [Templates](../reference/templates.md).

A few rules hold for some rows:

- "Command" is the word for what you invoke by slash.
  "Skill" is the word for the file shape, commands and contracts alike.
- A skeleton named `<type>-definition.md` is the skeleton of the
  definition of one member of a type the forge can be extended by.
  The types are an artefact, a critic lens, a challenger persona and
  a check.
- A lens, persona or check file carries its front-matter and its Lens
  section and nothing else.
  The shared rules come from the contract it names.
- The scripts are the door to a write of git.
  Reading git directly is open.
  The git hook holds the line between the two: it denies every write
  and names the script to use.
- `tmp/` is in git with its own `README.md` and `.gitignore`, so that
  it exists on every clone.
  Its contents never are in git.
  Nothing in it is a source of truth.
  A run in it is kept for inspection and deleted by hand, never by a
  script.

## What happens

One line of flow runs through the layer:

You type a command → Claude Code loads its skill beside the always-on
`CLAUDE.md` → the skill reads the definitions and templates it needs,
launches agents with their contracts and runs scripts → the scripts
do the deterministic work, git among it → the result lies in Markdown
files of the project.

Five ideas carry it:

- One always-on core, and everything else read when its situation
  arises.
  `CLAUDE.md` is loaded into every session and every subagent.
  A command, a definition, a contract or a template is a file read
  when it is invoked.
  What must hold through a long conversation is repeated by a hook at
  every prompt.
  Why the core is kept small is explained in
  [How the rules are held](../about/how-the-rules-are-held.md).
- State lives in Markdown files of the project, never in the
  conversation and never in the assistant's memory.
  A project is a directory: the artefacts of the chain, their history
  logs, the ledger, the records of the reviewers and the resources.
- Isolation is bought with subagents.
  A reviewer, a check and a render each run in a subagent.
  All of them run on the one session model.
- Git, the conversion of documents and the hooks are scripts.
  The scripts run on Python 3.8 or newer and use nothing Windows-only.
  What several scripts share lives in one module beside them, never
  twice.
- Every file has a way of merging, and the forge tells git which.
  Composed text and the record files merge as text.
  Derived state is made at read time and never kept in git, or made
  only on `main` and taken as ours at a merge.
  Immutable files never conflict.
  Where git leaves a conflict, Claude lays both sides out and the
  principal decides; the forge merges nothing itself.

What `docs/` and its map are is explained in
[The documentation](../about/the-documentation.md).

## A worked example

This traces one save of a project, `/save my-project`, through the
layer.

1. You type the command.
   Claude Code already holds `CLAUDE.md`, and the per-prompt hook from
   `.claude/settings.json` has run `scripts/hook-walkthrough.py`.
   You should now see Claude working from the save command's skill,
   `.claude/skills/save/SKILL.md`, which loaded only now.
2. The save runs the check `light`, because no `--quick` was given.
   Claude launches the agent `.claude/agents/check-light.md` as a
   subagent.
   The contract `.claude/skills/check-contract/SKILL.md` is preloaded
   into it at launch.
   You should now see the check's report come back: the agent is
   read-only and writes nothing itself.
3. Where the check finds something, the check procedure gives the
   findings their IDs and files the report.
   You should now see the report under the project's `reviews/`.
4. The save commits and pushes through `scripts/forge-save.py`.
   A direct write of git by Claude would be denied by the git hook,
   `scripts/hook-git.py`, which names this script instead.
   You should now see the commit on the branch that is checked out.
