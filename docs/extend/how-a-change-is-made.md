# Make a change to the forge

A change to the forge is a change of how it behaves, such as a
command, a rule, a convention or what a reviewer looks for. Such a
change is written down before it is built: first what is wanted and
why, then how it is solved, then the files that carry it out. This
page is for the extender, the reader who wants to change what the
forge does. It gives the order of the work, the commands that prove
it, where it is recorded, how it is released, and what a pull request
carries when the change is sent to the public engine.

## When to use it

Use this way when the change alters what the forge does. The line
between the kinds of change is drawn by what the change does, never
by its size.

- **A change of how the forge behaves** goes through the chain before
  it is built. The chain is the row of versioned documents a thought
  travels through (see [Glossary](../reference/glossary.md)). For the
  forge itself it is the intent and the solution design of the
  forge's own project. The rest of this page is about this kind.
- **A change that alters no behaviour** (a wording, a broken path, a
  slip) is made directly. Sent as a pull request, it goes as it is,
  with one sentence saying what it fixes. Nothing else is needed.
- **A change of a generated document** goes into the file the
  document is generated from, never into the document itself.
- **Feedback, an idea or a defect** needs no change from you. The way
  is `CONTRIBUTING.md` in the root of the engine.

In your own clone you decide everything: the forge there is yours.
What is merged into the public engine is decided by its author.

### Generated documents

`README.md`, `RELEASE-NOTES.md` and `CONTRIBUTING.md` are renders. A
render is a file generated from its recipe, the versioned file in
`projects/forge/recipes/` that says how the render is made. A render
is never edited by hand. A change goes into the recipe or into what
the recipe reads, and the file is regenerated:

- `README.md` and `RELEASE-NOTES.md` are regenerated by every
  release.
- `CONTRIBUTING.md` is regenerated on `/render contributing`, and not
  by a release (see [Render an output](../use/render-an-output.md)).
  Where Claude cannot tell the project from the conversation, name
  it: `/render contributing forge`.

A recipe is a versioned document. A change of a recipe is recorded in
the history companion of the recipe, as step 3 below describes.

The pages of `docs/` are generated the same way, by `/document` from
the files that own each topic, and a fix of a page goes into the file
the page mirrors (see
[Change a documentation page](change-a-documentation-page.md)).

### Feedback and ideas

`CONTRIBUTING.md` names the channels by kind:

- a discussion for feedback and for an idea;
- an issue for a defect;
- a private way for what is not public.

It points at two fixed files of the root (see
[The security policy and the code of conduct](../about/the-security-policy-and-the-code-of-conduct.md)).
A security problem never goes into an issue: it takes the way
`SECURITY.md` says. The code of conduct, `CODE_OF_CONDUCT.md`, holds
everywhere the forge is talked about.

## What you do

The change begins with one line, typed as it stands:

```
/forge intent forge
```

`forge` is the slug of the forge's own project. The whole way, in
order:

| Step | What you type | What it gives |
|---|---|---|
| 1. The forge's own project beside the engine | `/import-project <git-url>` | the directory `projects/forge` |
| 2. A branch, for a change of more than a few lines | `python scripts/forge-branch.py forge <name>` | the branch the change is saved on |
| 3. The position | `/forge intent forge` | the position in `projects/forge/10-intent.md`, with its record |
| 4. The item of the design | `/forge solution-design forge` | the item in `projects/forge/40-solution-design.md`, with its record |
| 5. The operating layer | the change itself | the changed files of the engine, a script with its test |
| 6. The proof | `/test`, `/check engine`, `/check single-source-of-truth` | the sum of the tests and the result of each check |
| 7. The release | `/release forge` | two commits, one in the engine and one in the project |

## What happens

1. **Bring the forge's own project beside the engine.** The intent
   and the solution design live in the forge's own project,
   `projects/forge`, which is a git repository of its own (see
   [Projects and the engine](../about/projects-and-the-engine.md)).
   The files of the engine live in the engine. A user of the engine
   never needs the project. Whoever develops the engine clones it
   beside the engine. The commands of a developer read it:

   - `/check engine`
   - `/document`
   - `/release forge`
   - `/new-artefact`
   - the renders of the README, the release notes and CONTRIBUTING

   Type `/import-project <git-url>` with the address that the
   engine's `projects/README.md` carries (see
   [Bring in an existing project](../use/bring-in-an-existing-project.md)).
   The clone runs on your word and lands in `projects/forge`. The
   command writes nothing into the project.

   You should now see the directory `projects/forge`, the commit
   identity git resolved for it, and the recommendation to begin
   with `/forge forge`.

2. **For a change of more than a few lines, make a branch first.**
   Type `python scripts/forge-branch.py forge <name>` (see
   [Work on a branch](../use/work-on-a-branch.md)). In the commands
   of git, `forge` names the whole: the repository of the engine and
   the project cloned beside it. You work and save on the branch, and
   the pull request is opened from the branch. The `main` of your
   fork then stays clean for the upgrades of the engine. The branch
   goes away with the merge.

   You should now see the work standing on the branch `<name>`, no
   longer on `main`.

3. **Write the position.** Type `/forge intent forge` (see
   [Forge the intent](../use/forge-the-intent.md)). The intent is the
   document that says what is wanted and why, and a position is one
   item of it. A change of substance goes into the intent first and
   propagates down the chain from there, whichever layer showed the
   need for it. Before it proposes a change to an existing position,
   Claude reads the history of that position. Before the write, it
   shows you the new wording and the records.

   Each record is written in the same step as the change, through
   the record script `scripts/forge-record.py`, never by an edit. It
   lands in the history companion, the append-only file
   `<file>.history.md` beside every versioned document (see
   [Versioning and history](../about/versioning-and-history.md)). The
   document holds the current state. The way to it goes into the
   record: why it changed, what was said, what was tried.

   You should now see the position in `projects/forge/10-intent.md`
   and its record in `projects/forge/10-intent.history.md`.

4. **Write the item of the solution design, where the change solves
   something.** Type `/forge solution-design forge`. The solution
   design is the document of the same project that says how a thing
   wanted is solved and in which files. Its record is written the
   same way.

   You should now see the item in
   `projects/forge/40-solution-design.md` and its record in the
   history companion beside it.

5. **Build the change in the operating layer.** The operating layer
   is these files of the engine:

   - `CLAUDE.md`
   - the skills under `.claude/skills/`
   - the agents under `.claude/agents/`
   - the templates under `templates/`
   - the scripts under `scripts/`

   A script is changed with its test in `tests/`. The tests are kept
   in the engine, beside the scripts they test.

   You should now see the change in the files of the engine and, for
   a script, its test changed with it.

6. **Prove it.** Three commands prove a change, each in its own way.

   - `/test` proves a script (see
     [Run the tests](../use/run-the-tests.md)). It runs
     `python -m pytest` over `tests/` from the root of the engine,
     and you may type that line yourself. It reports the sum as
     pytest prints it. It fixes nothing and changes nothing of the
     engine or of a project. The same tests run in CI at every push.
   - `/check engine` proves that the engine agrees with itself and
     with the forge's intent: every position honoured, nothing
     withdrawn still advertised, every decision reflected (see
     [Check conformance](../use/check-conformance.md)).
   - `/check single-source-of-truth` proves that every rule,
     procedure and file shape is written in one place and cited
     everywhere else. It reads the whole operating layer and is long
     by design. It fits before a major (an approved version, which
     carries an integer) or after a round of work on the operating
     layer, not at every release.

   You should now see the sum pytest prints, with no failed test, and
   from each check either that it passed or its findings.

7. **Release.** Type `/release forge` (see
   [Release a version](../use/release-a-version.md)). A release runs
   on `main` only. `forge` means the whole here too: the engine and
   the project beside it. Among its steps, in order:

   - It runs the tests of the engine first, before any check. A red
     test stops the release.
   - It runs the checks: `engine` on the engine, `light` and
     `project` on the forge's own project. Findings are settled by
     walkthrough, that is one finding per message, each closed by
     your verdict.
   - It reports the age of the documentation and offers `/document`
     (see
     [Generate the documentation](../use/generate-the-documentation.md)).
     The pages are regenerated on your word only.
   - It regenerates the README and the release notes from their
     recipes, every time, and tells you what materially changed. You
     rule on the difference before the commit. No other render is
     regenerated here, `CONTRIBUTING.md` included.
   - It saves the engine and the project as two commits. The renders
     of the project's recipes land in the root of the engine. One
     commit therefore holds the documents of the project, the other
     the derived files of the engine. The message of the release is
     drawn from the records of the intent's history since the last
     release. At an approved major the tag is proposed and taken on
     your word, one name in both repositories.

   You should now see two commits, one in the engine and one in the
   forge's own project, and `README.md` and `RELEASE-NOTES.md`
   regenerated in the root of the engine.

A change of the process is complete only once the intent is updated
and the README re-rendered.

### Where the change needs a test

Where a change of the operating layer needs a test, steps 3 to 5 run
in another order:

1. The brief comes first, in the principal's words. A brief is the
   document a matter is first written down in. The principal is the
   person whose thinking is forged and who decides: in your own
   clone, you.
2. The build and its test come next.
3. The rounds of the intent and of the design (the work of steps 3
   and 4) follow right after it, never across a release.

### If you send the change as a pull request

A change for the public engine stops before step 7 and is sent as a
pull request. `CONTRIBUTING.md` gives the way step by step, from the
fork of the repository to the pull request opened from it. The
easiest way is to open a discussion first. Whoever is unsure stops at
the discussion, and the author makes the change.

A pull request carries one matter and what that matter needs, never
several unrelated changes. A second matter goes in a second pull
request. Each can then be judged, merged or declined on its own.

For a change of behaviour the pull request carries:

- the position in `projects/forge/10-intent.md`, saying what is
  wanted and why, with its record in the history beside it;
- the item in `projects/forge/40-solution-design.md`, where the
  change solves something;
- the change itself, a script with its test;
- a description in plain words of what it changes and why, item by
  item, and of what was run, a script's test among it.

The description lets the change be judged without reading it line by
line. A pull request without it is sent back to be described.

A change that touches both repositories is two pull requests:

- one on the engine, with the change itself;
- one on the forge's own project, with the position and the item of
  the design.

Each names the other. The two are merged both or neither, in one
sitting: the project first, the engine second, and no release between
them. The reason: git merges no two repositories as one. Where one of
them is declined, both are closed with the reason.

A pull request carries no release and no regenerated README, release
notes or documentation. The author makes them at the next release. A
brief may come first and need not.

Everything that enters the forge's own project is written in English,
a brief included. The rule that a brief keeps the language it was
written in holds for your own instance (one installation of the
forge), not for the public project. A brief sent in another language
is translated at the merge, and its original stays in git.

Try your change yourself before you send it. A change written with an
AI is welcome on the same rule, and the pull request says what was
run.

## What you have afterwards

- A position in the intent that says what is wanted and why, with its
  record in the history companion.
- The item of the solution design, where the change solves something,
  with its record.
- The change in the operating layer, a script together with its test.
- After a release: the README and the release notes regenerated, and
  two commits, one in the engine and one in the forge's own project.
  At an approved major, one tag of the same name in both.

## If something goes wrong

- **`/import-project` stops and reports that the directory exists.**
  `projects/forge` is already there. Nothing is cloned.
- **`/import-project` says that git resolves no identity.** Git has
  no name and e-mail to sign commits on this host, and a save commits
  nothing until git resolves one. The login that cloned the
  repository is a different thing. The usual causes and the ways out
  are in the identity step of `/setup`.
- **`/test` says the tests did not run (`No module named pytest`).**
  The test runner is the one thing a contributor installs beyond
  `python`: `python -m pip install pytest`.
- **A test is red.** `/test` reports it word for word as pytest
  printed it, the failing assertion included, and fixes nothing. The
  fix is a round of its own: the script is changed with its test.
- **`/release forge` stops and names a branch.** A release runs on
  `main` only. It says how to get back:
  `python scripts/forge-branch.py forge main`, after saving.
- **`/release forge` refuses a repository behind or diverged from
  its origin.** It offers `/pull`.
- **A red test stops the release.** The failures are reported as
  `/test` reports them. You go back to the fix, and the release does
  not run.
- **pytest is missing at a release.** The release says that the tests
  did not run and goes on only on your word.
- **A check finds something.** A check is advisory. At a release the
  findings are settled by walkthrough. A finding may be parked, and
  the release proceeds. A finding you have not settled when you order
  the release to go on is parked by that word, and Claude says so.
- **`/check engine` finds a claim in the README that `CLAUDE.md` or
  the intent no longer supports.** That is a defect of the recipe. It
  is fixed in the recipe.
- **`/render contributing` reports a hit of its scan for facts of the
  instance.** You judge the hit. A fact of the instance is
  regenerated out, never edited out by hand.
- **A pull request is sent back.** It lacks the description of what
  it changes and why, and of what was run. Describe it and send it
  again.
- **One of two pull requests is declined.** Both are closed, with the
  reason.

## A worked example

The change below is invented: the forge has no such rule. It is
small, it changes what a command does, and it touches both
repositories.

The wish: after a clone, `/import-project` closes by naming the
README of the project as the first file to read.

1. The forge's own project is not yet on the machine. You type
   `/import-project <git-url>` with the address from
   `projects/README.md`. The directory `projects/forge` appears.
2. With the position and the item counted in, the change is more than
   a few lines. You type
   `python scripts/forge-branch.py forge readme-hint`.
3. You type `/forge intent forge` and say what you want and why.
   Claude shows the wording of a new position and its record. The
   position: after a clone, the forge names the README of the project
   as the first file to read. Its reason: whoever brings in a project
   he did not write does not know where to begin. The position lands
   in `projects/forge/10-intent.md`, the record in
   `projects/forge/10-intent.history.md`.
4. You type `/forge solution-design forge`. The item says where the
   sentence stands: in the last step of
   `.claude/skills/import-project/SKILL.md`. Its record lands in the
   history companion of the design.
5. The sentence is added to `.claude/skills/import-project/SKILL.md`.
   No script changes, and so no test changes. Had the change touched
   a script, its test in `tests/` would have changed in the same
   step, and `/test` would have been run.
6. You type `/check engine`. It reads the engine against the intent
   and reports that the check passed: the skill honours the new
   position. The round touched the operating layer, and
   `/check single-source-of-truth` fits as well where there is time
   for it.
7. In your own clone you type `/release forge`. The tests run first,
   the checks follow, the README and the release notes are
   regenerated, and the engine and the project are saved as two
   commits. The intent is updated and the README re-rendered: the
   change is complete.

Sent to the public engine, the same change ends differently after
step 6. You save with `/save`, which pushes the branch to your fork,
and open two pull requests from the branch:

- one on the forge's own project, with the position, the item and
  their records;
- one on the engine, with the changed skill.

Each names the other. The description of each says in plain words
what changes, why, and that `/check engine` was run. The author
merges both in one sitting, the project first and the engine second,
and makes the release.
