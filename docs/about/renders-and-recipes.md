# About renders and recipes

This page explains what a render and a recipe are in Forge of Thought,
how the two work together and why they are shaped as they are. It is
for anyone who uses the forge, extends it or weighs whether to adopt
it. It was put together from the Renders part of Document chain in
`CLAUDE.md`, the recipe skeleton `templates/recipe.md` and the
positions and one rejected direction of the forge's own intent,
`projects/forge/10-intent.md`, which give the reasons.

## What a render is

A render is an output made for one audience from the documents of the
chain: a pitch for a group, an architecture picture, an executive
summary, the repository README. It is generated, never written. A
render assigns nothing and is not part of the chain: the artefacts of
the chain stay the only source of truth, and a render is never a
source of truth of its own.

A render is never edited by hand. When its content is wrong, the fix
goes into its recipe or into its inputs, and the render is generated
again.

## What a recipe is

What is iterated is the render's recipe, a file at
`recipes/<recipe>.md`. One file holds everything a render is made
from:

- **Inputs:** the artefacts the render is generated from, by path,
  one per line. More than one input is legitimate, for example the
  intent together with the assignment.
- **Instructions:** audience, tone, what to emphasise, what to omit,
  target length, register: everything the renderer must know beyond
  the template.
- **Format:** optional. It names the file format (`pptx` or `docx`)
  and what each of the two making steps needs (below). A recipe
  without this section ends at the Markdown.
- **Template:** the literal skeleton of the render, with
  placeholders, always Markdown.

The front-matter carries the recipe's purpose and audience, its
version and an `updated` date. A recipe is a tool, not a record of
thinking: it is versioned so that a render can cite it, but it is
never approved, carries no status and stays at a 0.x version for
life. Like every versioned document it keeps its history in a
companion file beside it. Recipes are written in English; a render
may be in any language its recipe declares.

### Why a recipe is deliberately loose

A recipe's template fixes the structure and what information appears
where, never the wording: a presentation recipe says what belongs on
a slide, not how it is phrased. Every rendering derives the words
anew from the current inputs. Fixing the text in the template would
turn the recipe into the render and make its inputs meaningless.

The one exception is wording that carries weight. A recipe may pin
such wording as fixed text, a title, a claim, a fixed line, and what
is pinned comes out word for word at every regeneration, while
everything else is derived freely. Why this is needed is said under
"When a render is regenerated" below.

## Where a render ends and the chain begins

The boundary between the chain and a render is authorship, not
audience. A document the principal (the person whose thinking is
being forged) composes is a layer of the chain; a document generated
from artefacts is a render. An article the principal writes is
therefore a layer of the chain, and its translation is a render.

## Provenance and staleness

Every render opens with its provenance: it cites its recipe and every
input, each with its version. This is what lets the forge tell
whether a render still matches what it was made from. The project's
ledger mirrors the provenance in its Renders table, and its Published
table says of each designed file what it was made from and whether it
is `current` or `stale`.

A render may itself be an input of another render, for example a
slide of a deck citing an architecture picture. The citing recipe
must declare the other render among its Inputs, so that provenance
and staleness follow the dependency.

## When a render is regenerated

A render is regenerated only on the principal's explicit word, by the
render command, or by a release. Claude never regenerates a render
on its own judgement: it reports that a render is stale and offers to
regenerate it.

The reason is that regeneration is stochastic. The same inputs never
guarantee the same words, so a regeneration nobody has looked at is
an edit of an outward-facing document nobody has looked at. The
forge answers this with two light defences, neither of which blocks
anything:

- a recipe pins the wording that carries weight, as said above;
- a release that regenerated renders reports in its summary what
  materially changed in them, so that the principal rules on the
  difference before the release is committed, without reading a full
  diff.

The README and the release notes are regenerated by every release.
Every other render stays as stale as the principal lets it be; no
check reports the staleness of a render, and the project's state map
shows it.

One alternative was weighed and rejected: regenerating, at every
save, only the renders whose recipe or inputs had moved, with a mark
in the ledger for a render skipped on the principal's word. It would
have spared perhaps a third of the engine's saves and nothing on
projects, whose README input, the ledger, moves at every operation,
and it would have added a staleness state that several commands must
all read alike. A plain save that renders nothing and a release that
renders everything save the same and add nothing.

## Everything is Markdown: two steps to a file

Everything the forge produces is Markdown, renders included: a
presentation is a Markdown file saying what is on each slide, with
diagrams for the pictures. The forge ends at content but carries, at
its edge, tools that turn a Markdown render into a PowerPoint or a
Word file. All other format conversion stays outside the forge.

An output is made in two steps, each with its own command, divided
by cost so that the expensive step runs as seldom as possible:

1. **The plain file.** `/render` generates the Markdown and, where
   the recipe names a format, the plain file beside it through
   pandoc. This is deterministic and cheap, and can be repeated
   freely.
2. **The designed file.** `/publish` makes the designed file through
   a model and its document skills, into `published/`. It is
   expensive and runs only on the principal's command: never as part
   of rendering, never as part of a release and never on Claude's own
   judgement. It makes a file and sends nothing anywhere.

`/publish` takes the render as it lies on disk and never renders
first. A render is made by a model and is never the same twice, so a
fresh one would publish a text the principal has not read. If the
render is stale, this is said before the conversion and the decision
is the principal's.

The format and what each step needs stand in the recipe's Format
section, so the render itself carries content only and the
instructions for the model stay in the recipe. Plain and designed
files are tracked in git like any render and are never edited by
hand: the Markdown render stays the source of truth.

## Every project's README and release notes

Every project has a README that is a render of its own
`recipes/readme.md`, written to the project root. A thought project
also has release notes, a render of `recipes/release-notes.md`. This
is the same mechanism the engine uses for its own README and release
notes: the recipe is what is iterated, the render is never edited by
hand, and every release of the project regenerates both. A library
has a README only, a catalogue of what it holds, since release notes
are derived from the history of an intent and a library has none.

Release notes are a log of releases, not a story: one section per
release, newest first, one sentence per change from the reader's
side, derived from the history records since the previous release.
What the reader must do is never derived: it is written with the
change and carried into the notes word for word.

## Composing a recipe by genre

A recipe may be composed through a genre interview: one definition
per genre carries the questions to ask, and the genre's skeleton
extends the base recipe shape without replacing it. The first genre
is `presentation`, a slide-by-slide deck whose render is turned into
a PowerPoint file. The README and release notes recipes are genres
too, set up when a project is created.
